# OIP-008.5 — Schema6 and preservation

Append-only migration6 adds inventory_devices, inventory_by_site_id and inventory_audit. Migrations1–5 and Cargo.lock remain unchanged. Inventory rows use a stable DeviceId PK, Site FK, typed bounded metadata JSON, registration/origin constraints, timestamps, registrar FK and positive revision. Organizational parents are resolved through Site; no redundant tenant IDs can conflict. Triggers keep ID/site/origin/original registrar/time immutable and prevent deletion of source-referenced inventory. No deletion method is exposed.

Existing SourcePlacements backfill the **same IDs**. Stored source origin determines ExistingSimulationSource or ExistingExternalSource; physical type is Other. No current-time/actor is fabricated. Exact old names up to16KiB are preserved, including Unicode; larger legacy names fail migration6 inside its transaction with an explicit operator-review error, leaving the old schema/data intact. Manual input limits remain128 bytes. This is fail-closed preservation, not silent truncation or repair.

Provisioning synchronizes new source identities to inventory in the **same transaction**, with conflict handling only for an existing ID. It cannot suppress unrelated constraint violations. A source cannot bind an existing manual device in a different Site; original placement/IDs remain immutable. Same-site association to an existing device preserves its metadata/origin/revision; it creates no fake device. Runtime loading checks inventory/source placement consistency before workers start.

Local administration acquires the canonical private DatabaseOwnership guard. Dry-run/query/cleanup paths use read-only connections, reject missing DBs and require an already supported schema; they do not migrate or create CoreRuns/writers. `--inventory-initialize` is a separate explicit OS-operator step with a persisted scoped InventoryManage grant. Runtime-open also performs normal versioned migrations. There is no remote migration API.

Import/apply validates the complete bounded batch, all permissions/parents and all CAS revisions before writing. Value changes and per-device audit entries commit atomically. Any later write/audit error rolls back the whole batch. Stable IDs are the duplicate key; names/IPs are not unique identities. Existing nonidentical entries require explicit Update and expected_revision. Register replay is a no-op without duplicate rows/audits. All counts/old keys remain untouched by registration/archive except intended inventory/audit data.

Audit records contain actual time, OS operator UID authority, selected on-behalf policy principal, device FK, operation and revision. No full metadata or credentials are logged there. It is atomic but not tamper-proof/durable security certification. The OS owner can select a provisioned policy principal; this is an explicit local administrative trust boundary, not authenticated remote identity.

Real migration evidence uses a protected **exact OIP-008.4 binary** to generate schema5 with four actual simulator processes, two Organizations, historical events/gaps/health and a persisted setting. Schema6 preserves every old row/key/payload and policy, adds four source-origin inventory rows, passes FKs/integrity and idempotent reopen. A schema5 dry run is rejected without changing DB bytes/schema. Failure-injection tests cover6-DDL rollback, settings preservation, Unicode/oversize legacy names, invalid new-source projection, duplicate import, partial-write/audit rollback and source/site integrity. No operator DB is used by these tests.
