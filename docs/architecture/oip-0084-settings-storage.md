# OIP-008.4 — Storage and offline apply

Append-only migration5 `typed_application_settings` follows the unchanged migrations1–4. It creates setting_scopes, settings and settings_audit. No historical table, payload, event/observation/gap ID, placement or health transition is rewritten by migration5. Offline hierarchy provisioning still may stop at3; normal runtime/storage opening applies the supported migrations through5. Do not mislabel offline provisioning as already applying the newest schema.

setting_scopes binds canonical serialized AccessScope exactly to its corresponding nullable FK (organization/infrastructure/site/source), or all-null Platform. CHECK uses the exact canonical JSON produced by the core enum; immutable-target trigger forbids alias/update reassignment. Parent deletion is restricted by FKs. settings uses scope/key composite PK, typed key allowlist, bounded JSON, positive CAS revision, creation/update time and on-behalf policy principal FK. Loader decodes and revalidates typed values and registered scopes before startup; at most2048 rows are admitted. Settings reads use this snapshot, no live SQL polling or extra writer.

The local CLI acquires existing canonical DatabaseOwnership **before opening/migrating** SQLite, reusing symlink/alias/single-writer protections. It cannot update a running daemon's database. Input file is read to4097 bytes and rejected above4096. Typed validation and HierarchyRegistry authorization run before an Immediate transaction. Revision comparison, scope creation, settings upsert and settings audit insert commit together. A failure after the upsert but before audit insert rolls back both. Concurrent commands either conflict at ownership or CAS; only one command can win the same expected revision.

SettingsChange is a typed **offline management contract**, not an executable remote CapabilityService mutation. Its descriptor requires SettingsWrite, mapping says OFFLINE_OPERATOR_ONLY, REST=false, MCP=BLOCKED. SqliteStore's narrow administration method reuses core key validation and central HierarchyRegistry permission resolution. No generic settings.write bypass or new policy/credential fields exist.

## Authority and audit

The authenticated authority is the local OS operator with private DB ownership. JSON principal is an explicit **on-behalf policy selection**, not proof that a remote principal authenticated. settings_audit separately records actual protected-file owner UID established by existing ownership checks, selected principal, scope/key, revision, time and outcome. No values/credentials are recorded in that audit table. This is atomic attribution, not a tamper-proof security ledger. Same-UID privileged processes remain trusted.

Normal change result contains the persisted record plus persisted_requires_restart and no effective runtime value. The next successful runtime start reads/validates the stored state; no deferred unbounded task, polling loop or separate apply engine exists. A crash before commit retains the old value; SQLite transactions/WAL recover committed changes. A failed startup never claims Ready. No rollback endpoint is added: an authorized subsequent offline CAS can deliberately restore a prior safe value using the then-current revision.

Tests cover real4→5 history-preserving migration, unchanged keys/payloads/FKs/ledger, DDL failure rollback/idempotency, settings/audit failure rollback, CAS, simultaneous CLI commands, restart and SIGKILL. Protected schema4 binary provenance and disposable DB backup are in the external receipt. No operator DB was opened.
